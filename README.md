# crazyflie-sim
CrazyFlie simulation with Gazebo and ROS2 support.

Software version: 
- **ROS 2:** Humble [[docs](https://docs.ros.org/en/humble/index.html)]
- **Gazebo:** Harmonic [[docs](https://gazebosim.org/docs/harmonic/getstarted/)]
- **CrazySim:** 1.2x (commit `8ad9bb8`) [[repo](https://github.com/gtfactslab/CrazySim/tree/8ad9bb8dfe8c827f349b3a224d47f7808c186d06)]

> [!NOTE]
> This repository is prepared for working with Ubuntu OS. 
> If you are using Windows, please open Ubuntu in WSL 2.
> However, you are doing this on your own risk :smile:.

## Prerequisites

First of all, before you start anything, please fork this repository and **work on your own copy**.

The best way to work with this repository is to use the prepared Docker image.
Follow the official [Docker Documentation](https://docs.docker.com/) to install the required software (note that on Linux, only the Docker Engine is required).
Also, if you have an Nvidia GPU and want to use its computing power within Docker, you should install the [Nvidia Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html) (without experimental packages and rootless mode).

> [!NOTE]
> If you do not have an Nvidia GPU card, you need to modify the [devcontainer.json](.devcontainer/devcontainer.json) and set `"dockerComposeFile"` to `compose.nogpu.yaml`.

## Docker run

> [!TIP]
> In Windows, it is recommended to use WSL2 with a native Linux file system.
> Normally directories from Windows are mounted as `/mnt` inside Ubuntu, but this may cause some problems due to the NTFS file system and permissions.
> Therefore, copy repository or clone it directly into `$HOME` directory inside WSL2.

Open the project's directory in VS Code.
In the bottom left corner, click on the icon with the two arrows pointing at each other.
The menu with different options will appear at the top - choose **"Open folder in container... "** and wait, the docker will be created.
Note that this may take some time (depending on your internet connection).

Next time, you can open Docker again in the same way, but it should take considerably less time because of the cached image.

## Native installation on Ubuntu 22.04

This section explains how to run the project directly on Ubuntu, without
Docker. The native workflow uses this repository as the ROS 2 workspace root:

```text
crazyflie-sim/
|-- src/
|   `-- evs_gz_utils/       ROS 2 package
|-- vendor/
|   `-- CrazySim/           pinned non-ROS dependency
|-- .venv/                  local Python environment (not committed)
|-- build/                  generated by colcon (not committed)
|-- install/                generated by colcon (not committed)
`-- log/                    generated by colcon (not committed)
```

`CrazySim` is kept outside `src` because it is not a ROS package. Restricting
colcon to `src` prevents colcon from trying to build the Python and firmware
projects inside `vendor/CrazySim` as ROS packages.

### Native prerequisites

The tested native platform is Ubuntu 22.04 with:

- ROS 2 Humble
- Gazebo Harmonic
- `ros-humble-ros-gzharmonic`
- Python 3.10
- CMake, a C/C++ compiler, Git, and colcon

ROS 2 and Gazebo must be installed from their package repositories before
continuing. The main packages used by this repository can then be checked with:

```bash
lsb_release -ds
python3 --version
ros2 --help >/dev/null && echo "ROS 2: OK"
gz sim --versions
colcon --help >/dev/null && echo "colcon: OK"
```

On a configured Ubuntu 22.04 system, the remaining development packages can be
installed with:

```bash
sudo apt update
sudo apt install build-essential cmake git libbullet-dev python3-pip python3-venv python3-colcon-common-extensions python3-vcstool python-is-python3 ros-dev-tools
```

Gazebo Harmonic is not the default Gazebo release paired with ROS 2 Humble.
This project intentionally uses the `ros-humble-ros-gzharmonic` packages from
the Gazebo package repository.

### Clone the complete project

The `evs_gz_utils` and CrazySim repositories are Git submodules. A fresh clone
must therefore include `--recurse-submodules`. While the native work is on its
feature branch, clone that branch directly so Git initializes the submodules at
their new paths:

```bash
git clone --recurse-submodules --branch feature/native-install git@github.com:Darkjrcy/crazyflie-sim.git
cd crazyflie-sim
```

After the feature branch is merged into the repository's default branch, the
`--branch feature/native-install` part will no longer be needed.

For the existing checkout used to develop this branch, refresh all submodules
with:

```bash
git submodule update --init --recursive
```

For an existing checkout, only the second command is needed after pulling a
commit that changes a submodule.

Confirm that CrazySim is at the version tested by this project:

```bash
git -C vendor/CrazySim rev-parse --short HEAD
```

The expected result is `8ad9bb8`.

### Create the Python environment

Create the virtual environment only once per checkout:

```bash
python3 -m venv --system-site-packages .venv
source .venv/bin/activate
export PYTHONNOUSERSITE=1
python -m pip install --upgrade pip
python -m pip install -r requirements-native.txt
python -m pip install -e vendor/CrazySim/crazyflie-lib-python
```

`--system-site-packages` makes the ROS Python packages installed by `apt`
available inside the virtual environment. `PYTHONNOUSERSITE=1` prevents
unrelated packages from `~/.local` from overriding the versions pinned in
`requirements-native.txt`. The editable `cflib` installation makes Python load
the CrazySim-specific library directly from `vendor/CrazySim`.

Verify the environment:

```bash
python -c "import cflib, numpy, numba, quaternionic; print('Native Python environment: OK')"
```

### Build CrazySim

The upstream CrazySim build and launch files do not quote all filesystem paths.
Consequently, they fail when the repository is below a directory containing
spaces, such as `FALL 2026/AE 626`. This repository supplies a build wrapper
that creates a stable, no-space symbolic link under `/tmp` before calling
CMake. The source files and build results remain in this repository.

Configure and compile the modified Crazyflie firmware and Gazebo plugins with:

```bash
./scripts/build-crazysim-native.sh
```

The wrapper verifies that `sitl_make/build/cf2` was produced. Run it again after
changing the CrazySim firmware or its Gazebo plugins. CMake reuses the existing
build directory and recompiles only what is needed.

### Build the ROS 2 workspace

Load ROS and build only the packages located under `src`:

```bash
source /opt/ros/humble/setup.bash
colcon build --base-paths src --merge-install --symlink-install --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

The command above is intentionally shown on one line. `--base-paths` is an
option belonging to `colcon build`; it is not a command by itself. Running this
will fail:

```text
--base-paths src
```

If the build command is split across multiple lines, every continued line must
have a backslash at the end of the preceding line:

```bash
colcon build \
  --base-paths src \
  --merge-install \
  --symlink-install \
  --cmake-args \
    -DCMAKE_BUILD_TYPE=RelWithDebInfo \
    -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

Do not type the leading `--base-paths` line separately. A backslash must be the
last character on its line; spaces after it can break command continuation.

After a successful build, load the workspace and verify the package:

```bash
source install/setup.bash
ros2 pkg prefix evs_gz_utils
```

Build the ROS workspace again after changing code under `src` or after updating
its submodules.

### Environment setup in every new terminal

Creating and building the environment is normally a one-time operation.
However, shell environment changes do not carry over to a new terminal. In
every terminal used by this project, run:

```bash
cd "$HOME/JORGE/FALL 2026/AE 626/Project/crazyflie-sim"
source .venv/bin/activate
export PYTHONNOUSERSITE=1
source /opt/ros/humble/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=42
export CRAZYSIM_ROOT="$PWD/vendor/CrazySim"
```

Use a unique `ROS_DOMAIN_ID` from 0 through 101 when working around other ROS
users. Activating the environment does not rebuild anything; it only gives the
current terminal the correct Python, ROS, and project paths.

### Start the native simulation

The following examples use separate terminals. Perform the environment setup
from the previous section in each terminal first.

In terminal 1, start Gazebo and the Crazyflie firmware through the native
wrapper. The wrapper is required when any parent directory contains spaces:

```bash
cd "$HOME/JORGE/FALL 2026/AE 626/Project/crazyflie-sim"
./scripts/run-simulation-native.sh -m crazyflie -x 0 -y 0
```

Run only one simulation instance. Leave terminal 1 open after Gazebo starts;
the Python examples connect to that running process. The wrapper refuses to
start if it detects another Gazebo simulation or `cf2` firmware instance.

In terminal 2, run the connection and telemetry example:

```bash
cd "$HOME/JORGE/FALL 2026/AE 626/Project/crazyflie-sim"
python connection_example.py
```

In terminal 3, optionally start the ROS/Gazebo utilities:

```bash
ros2 launch evs_gz_utils model_state.launch.py world_name:=world_1 model_name:=uav
```

The native Gazebo process uses the host display and GPU directly. Docker-only
commands such as `xhost +local:docker` are not required.

If an error contains a truncated path such as `/home/jorge/JORGE/FALL: No such
file or directory`, a CrazySim script was started directly instead of through
the wrapper. Stop any remaining simulator processes and use
`./scripts/run-simulation-native.sh`.

If a Python example immediately prints `UdpDriver closed`, first confirm that
terminal 1 is still running both Gazebo and the simulated firmware. That line
means the client closed its UDP driver; it is not evidence of an estimator
failure by itself.

### Run the CrazySim flight demonstrations

Start the simulator in terminal 1 before running either example in another
configured terminal.

Square flight demonstration:

```bash
cd "$CRAZYSIM_ROOT/crazyflie-lib-python"
CFLIB_URI=udp://0.0.0.0:19850 python examples/autonomy/position_commander_demo.py
```

Figure-eight demonstration:

```bash
cd "$CRAZYSIM_ROOT/crazyflie-lib-python"
CFLIB_URI=udp://0.0.0.0:19850 python examples/autonomy/autonomous_sequence_high_level.py
```

### What is stored in Git

Commit source files, documentation, `.gitmodules`, and
`requirements-native.txt`. Do not commit `.venv`, `build`, `install`, `log`, or
compiled CrazySim files. Check this before every commit:

```bash
git status
git submodule status --recursive
```

Keep the Docker configuration until the native workflow has been tested from a
fresh recursive clone. It provides a known-working fallback while the native
installation is being developed.

## Reposiory content

### Docker system

Inside the Docker image, all the important files are stored in the `/root` directory.
There are two directories:
1. `/root/CrazySim` - containes the [CrazySim](https://github.com/gtfactslab/CrazySim/tree/8ad9bb8dfe8c827f349b3a224d47f7808c186d06?tab=readme-ov-file) software, which serves the purpose of SITL (*Software-in-the-Loop*) simulation for CrazyFlie drones.
Internally it uses the [Gazebo](https://gazebosim.org/docs/harmonic/getstarted/) simulator.
2. `/root/ros2_ws` - containes the ROS2 workspace where you can use all the ROS2 packages you want.
Note that the `/root/ros2_ws/src` is mounted directly on the local directory and containes the entire repository.
There you also have the [evs_gz_utils](https://github.com/vision-agh/evs_gz_utils) package with some utility functions to exchange data between Gazebo and ROS2.

### How it works (if only it worked)

CrazySim consists of the two main components:
1. [crazyflie-firmware](https://github.com/llanesc/crazyflie-firmware/tree/6a4d2d006ba3c394949582c1c2eedd4b84fce17e) - this is a piece of code that normally runs on the UAV.
Here it is also responsible for running the Gazebo simulator and spawning drones in it.
2. [crazyflie-lib-python](https://github.com/llanesc/crazyflie-lib-python/tree/9f50dce2dbba7d3836a86f6965095dbb43242a07) - this is on the other side of the communication channel, usually running on the so-called 'ground station' (i.e. something that does NOT fly).
With this library you should be able to read all the data from the CrazyFlie and transmit the control signals.

> [!TIP]
> You can easily change the directory to the `/root/CrazySim` using `cd_crazysim` alias.

In order to check if everything is working correctly, firstly spawn the UAV with CrazySim:
``` bash
cd_crazysim && cd crazyflie-firmware
bash tools/crazyflie-simulation/simulator_files/gazebo/launch/sitl_singleagent.sh -m crazyflie -x 0 -y 0
```

Secondly, in the separate terminal, run the [connection_example](./connection_example.py) script.
It should prints some data that is constantly read from the CrazyFlie in the simulation.

> [!TIP]
> Read the [How to use CrazySim](https://github.com/gtfactslab/CrazySim/tree/8ad9bb8dfe8c827f349b3a224d47f7808c186d06?tab=readme-ov-file#how-to-use) to learn how to use CrazySim :smile:.

### Where is ROS?

Yup, as you can see, no ROS is needed to control the CrazyFlie inside CrazySim.
However, one of your goals is to integrate CrazySim with the ROS infrastructure to facilitate further integration with other robotics software.
Before using ROS for the first time, setup the environment with the following command:
``` bash
cd /root/ros2_ws
source ./setup.sh <id>
```
As the `<id>` argument you need to provide the `ROS_DOMAIN_ID` (integer in the range 0-101, both inclusive).
If you are working in the lab, this value must be **original**, just for you.
This way you will only see your ROS topics and will not interfere with the topics of your colleagues.

Remember that before using ROS and after significant changes made in the workspace, you need to build the entire workspace.
To do so, just envoke the [build.sh](.devcontainer/build.sh) script, which is located inside `/root/ros2_ws` directory:
``` bash
cd /root/ros2_ws
./build.sh
```

You will then need to source the `/root/ros2_ws/install/setup.bash` script to make all the changes visible, but this is already done in `.bashrc`, so all you need to do is reopen the terminal.

## Additional features

### Data exchange between Gazebo and ROS2

Natively, Gazebo and ROS have a similar internal structure with topics and services to transport data, but they are not seamlessly interoperable (e.g. different types).
However, there is an additional [ros_gz](https://github.com/gazebosim/ros_gz) package provided by Gazebo developers, which facilitates integration between Gazebo and ROS.
It is already installed in the docker, so you can use all the features you need.

For your convenience, there is also an [evs_gz_utils](./src/evs_gz_utils/) package in the repository.
You can read its own (not very rich - still under development) documentation to learn more.

### Rosbag

If you are running nodes inside ROS2, you can easily record all the data that is exchanged via topics.
Just use the [rosbag2](https://github.com/ros2/rosbag2) which is already installed in the docker.
Remember that you can manually select the topics you want to record and set the path where all the bags will be stored.

### PlotJuggler

If you've recorded some rosbags, you'd like to be able to read and analyse them now, wouldn't you?
Fortunately, there is a good piece of software called [PlotJuggler](https://plotjuggler.io/) that is already installed in the docker.
You can run it with the following command:

```bash
ros2 run plotjuggler plotjuggler 
```
After some random meme, you will see the main window where you can import and plot data.
Some additional functions can be found in the linked documentation.
